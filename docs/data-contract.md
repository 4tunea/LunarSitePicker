# Data contract: precompute → frontend

Status: **APPROVED, schema_version "1.0" (2026-11-14). Changes go through the lead
(precompute owner).** The frontend (`app.js`) is built against this document; section 3 marks
every field it reads. A change to a marked field needs a matching change in `app.js`, so it is
agreed with the frontend owner first.

History: drafted as "DRAFT v1.0" on 2026-11-14 (the precompute branch called the same draft
v0.2). The frontend and the fake fixture use `"schema_version": "1.0"`, so that string stays.

`precompute/` writes **one file** that the frontend loads. It ships **angles, not
verdicts**. It contains terrain horizons and Sun/Earth positions. It has **no**
"available" / "visible" flags. The browser derives visibility so that thresholds stay
user-settable and the slip search runs on the client.

## 1. Files

| File | Content | Why |
|---|---|---|
| `web/data/navigator-data.json` | The JSON object below | For tools, tests and HTTP hosting |
| `web/data/navigator-data.js`   | `var NAV_DATA = <same JSON>;` | The app is opened as `file://`, where `fetch()` of local JSON is blocked. `index.html` loads it with a `<script>` tag. |
| `web/data/navigator-data.fake.js` / `.json` | Same shape, `"fake": true`, invented numbers | Lets the interface be built before real data exists. `index.html` loads the fake file first and the real file after it, so the real file wins when present. |

All are generated by one writer (`precompute/build.py`). Never edit them by hand. They are
small (see §6) and are **committed** so the static site works without running Python.
`.gitignore` must ignore only the top-level `/data/`, not `web/data/`.

## 2. Conventions (apply to every field)

| Quantity | Convention |
|---|---|
| Angles | Degrees unless the field name says otherwise |
| Azimuth | 0 = local north, increasing **clockwise** (east = 90, south = 180, west = 270). Range [0, 360). "North" means the direction of increasing latitude along the local meridian. At south-pole sites this points **away** from the pole. |
| Altitude / elevation angle | Degrees above the local horizontal plane. The horizontal plane is perpendicular to the radius vector through the site (spherical Moon, R = 1737.4 km). Negative = below the horizontal. |
| Latitude | Planetocentric, degrees, south negative, MOON_ME (DE421) frame |
| Longitude | **East-positive**, degrees, range **[-180, 180)**, MOON_ME (DE421) frame |
| Heights | Metres. Terrain heights are relative to the 1737.4 km reference sphere. |
| Distances | km (e.g. `max_range_km`) |
| Time | **UTC**, ISO 8601 with `Z` (e.g. `2026-11-01T00:00:00Z`). Times are not stored per sample (see §4). |
| Refraction | None anywhere (the Moon has no atmosphere) |
| Missing value | `null` (should not occur for the 5 analysed sites) |

### Horizon azimuth bins
- 720 bins, 0.5° apart. **Bin `i` is centred on azimuth `i × 0.5°`** and represents
  [i×0.5 − 0.25, i×0.5 + 0.25). Bin 0 is centred on north (0°) and covers 359.75–0.25.
- Each value is the **maximum over 3 rays** cast at the bin centre and at ±1/6° (the thirds of
  the bin), so a peak narrower than a bin is less likely to be missed. `horizon_grid.sampling`
  records this as `"max of 3 rays per bin"`.
- Rays march out to `max_range_km` = 250 km with bilinear sampling of the DEM and the exact
  spherical elevation angle (curvature included), for each mast height.
- Lookup at an arbitrary azimuth `az` (this is what `app.js` does): interpolate linearly between
  bins `floor(az/0.5) mod 720` and the next bin. Wrap 719 → 0.

### Ephemeris
- Sun and Earth positions are **apparent** topocentric positions: light-time and stellar
  aberration are applied, with no refraction. This matches JPL Horizons quantity 4
  (apparent Az/El), which we validate against.
- The observer is at the site's DEM ground height plus the mast height used for the ephemeris
  (2 m; 10 m moves the Earth by < 0.00001°, so one series serves both masts). Mast height
  matters only for the terrain horizon.
- Reference: Skyfield, DE421 + `moon_pa_de421_1900-2050.bpc`, frame `MOON_ME_DE421`,
  observer built with `pc.build_latlon_degrees(frame, lat, lon, elevation_m=...)`.

Rules the frontend relies on (checked in `app.js`, 2026-11-14):

- `sites[0]` is special. The app rebuilds the Moon-fixed Sun direction and Earth position from
  the first site's `lat_deg`, `lon_deg`, `ground_elev_m`, `sun`, `earth` and
  `bodies.earth.diam_deg`, and uses them for picked spots and past landings. The first site
  must therefore be a real analysed site with full-accuracy angles. Order: Connecting Ridge first.
- The mast selector is filled from `sites[0].horizons[].mast_height_m`; every site must list
  the same masts in the same order.
- `terrain` other than `"dem"` means no skyline: the app uses the smooth-sphere dip
  `-acos(R/(R+mast))`.
- Array lengths: `time.count` for every alt/az and diameter series, `horizon_grid.n_az` for
  every `elev_deg`. The app indexes without bounds checks.
- `dem[]` lists the near-field PGDA 5 m tile (`<label>_final_adj_5mpp_surf.tif`, 16–30 km wide)
  first and the far-field `LDEM_75S_120M.IMG` second; the horizon uses the finest layer that
  covers each point.

## 4. Time series

- Sample `k` (0-based) is at time `start_utc + k × step_s`, so times are not stored.
  2026-11-01T00:00Z is k = 0, and the last sample is 2028-02-29T23:00Z (k = 11663).
  The app derives everything from `start_utc`, `step_s` and `count` (checked: date limits,
  demo search, slider ranges all follow `count`), so the range can change without a UI change.
- Hourly. Between samples the frontend interpolates **linearly**. For azimuth it must
  unwrap across 360/0, e.g. 359.8 → 0.3 is +0.5°, not −359.5°.
- The Sun's azimuth at these latitudes moves ≈ 0.51°/h, about one horizon bin per hour.
  Linear interpolation gives sunrise/sunset times to within minutes. This needs to be
  confirmed once real data exists.
- End of data: a stay that runs past the last sample is shown as cut by the app
  (`status.cut`), never extrapolated.

## 5. Sun and Earth angular diameters

The frontend reads these from `bodies.*.diam_deg[k]`. **It must not hard-code them.**

| Body | Typical | Range over Nov 2026 – Feb 2028 (measured, first real run) | Stored as |
|---|---|---|---|
| Sun | 0.533° | 0.523–0.543° (Earth–Sun distance varies) | hourly series, 3 decimals |
| Earth | 1.90° | 1.795–2.048° (Earth–Moon distance 356–407 thousand km) | hourly series, 3 decimals |

- Diameters are stored as series, not constants. Earth's diameter varies by about ±7%,
  which matters at the edge of the disc.
- They are stored **once** (topocentric from Connecting Ridge), not per site. Between the
  5 south-pole sites the difference is < 0.0001°.
- Diameters use IAU nominal radii: Sun 695,700 km, Earth 6,371.0 km (mean). The app uses the
  same 6,371.0 km when it rebuilds the Earth position from the first site.

## 6. Encoding and size

- **Plain JSON number arrays.** No base64 or binary, so it can be debugged by eye.
- Alt/az and horizon values are rounded to **2 decimals** (0.01°; max quantisation error
  0.005°, well below horizon/DEM uncertainty). Diameters are rounded to **3 decimals**.
- Measured on the real file (2026-11-14, 11664 h, 720 bins × 2 masts, 6 sites):

  | | Size |
  |---|---|
  | One site (Connecting Ridge alone) | 0.43 MB |
  | Total, `navigator-data.json` | 1.87 MB |
  | Total, `navigator-data.js` | 1.87 MB |
  | Gzipped (as GitHub Pages / Vercel serve it) | 0.42 MB |
- This is under the ~3 MB budget, so no reduction is needed. If we add sites or a second
  year, these are the options, in order:
  1. Drop to 1 decimal for azimuth beyond ±30 days of the demo dates (≈ −10%).
  2. int16 (alt, hundredths) / uint16 (az, hundredths: 0–35999 does not fit int16)
     little-endian arrays, base64-encoded (≈ 0.5 MB total for 5 sites).
  3. One file per site, loaded on demand.

## 7. How the frontend derives visibility (reference formulas)

These are **not** in the file. They are defined here so every consumer computes the same
thing. This is what `app.js` implements (functions `skyline`, `fraction`, `vis`, `status`).

```text
h(az)      = horizon elevation at az for the chosen mast (interpolated, §2)
r          = diam_deg[k] / 2
x          = clamp((alt - h(az)) / r, -1, 1)
fraction   = 1 - (acos(x) - x*sqrt(1 - x*x)) / PI      // share of disc above the horizon line

sun_up[k]   = fraction_sun[k]      >= S          // S = required Sun disc fraction, default 0.5
earth_up[k] = alt_earth[k] - h(az) >  E          // E = required Earth clearance, default 0°
```

User settings, all with visible controls in the "Technical data" panel: mast height (from the
file's mast list, default the first), S (default 50%), E (default 0°), and a stay share P
(default 50%).

**"Available" for a landing at sample k0 with a stay of m samples** (the app's rule, stricter
than "both visible now"):

```text
available = sun_up[k0] AND earth_up[k0] AND (count of k in [k0, k0+m) with sun_up AND earth_up) / m >= P
```

Ranking of sites and the "next window" search use the same rule: alternatives are the other
sites that are available on the new date, ordered by the number of samples with both up during
the stay; the next window is the first later day (same hour) on which the site is available.

The fraction formula treats the horizon as flat across the disc. Earth's disc spans
~4 bins (§9).

## 9. Known limitations

- **No atmospheric refraction.** This is correct for the Moon, not a simplification.
- **Horizon accuracy is limited by the DEMs.** The near field (≈ ±8 km) uses 5 m/px
  PGDA tiles once downloaded. Beyond that it uses the 120 m/px LDEM_75S. Ridges narrower than a
  few pixels in the far field are smoothed out. Boulders and the lander itself are not
  represented. Interpolation errors at the 5 m / 120 m seam are possible.
- **Range cut at 250 km.** Terrain beyond 250 km is ignored. At the pole, distant
  massifs can still matter for grazing Sun angles. To be checked by comparing 150 vs
  250 km on one site.
- **Horizon sampled with 3 rays per 0.5° bin.** A peak narrower than about 0.17° between
  rays can still be missed.
- **Disc model is approximate.** The visible fraction assumes a flat horizon across the
  disc. Earth (~1.9°) spans ~4 bins, so the error is largest where the skyline is steep.
- **Hourly ephemeris** with linear interpolation. Event times are approximate to minutes.
- **Sixteen months only** (2026-11-01 to 2028-02-29). Dates outside have no data.
- **Sphere-only sites.** Sites outside the 75°S DEM (Apollo, Chang'e, Chandrayaan-3, …)
  have no terrain. None are in this file yet. `build.py` writes such a site (one that
  `on_dem()` finds outside every layer) as `"terrain": "sphere-only"`, `dem: []`,
  `ground_elev_m: 0`, and `horizons[]` with the same masts, `max_range_km: 0`, `complete: true`
  and `elev_deg` = the analytic dip, so the build never fails on it. The app ignores those
  horizons for any `terrain` other than `"dem"` and uses the smooth-sphere dip
  `-acos(R/(R+h_mast))` itself (≈ −0.087° at 2 m, −0.194° at 10 m), labels every verdict
  "smooth sphere, no terrain", and ranks such points, like past landings and pins, as
  reference points below the analysed sites.
- **Spherical Moon.** "Horizontal" uses the radius vector of a 1737.4 km sphere,
  consistent with the LOLA DEMs.
- **Ephemeris accuracy** is bounded by DE421 and the lunar orientation model. The
  measured difference to JPL Horizons will be in `validation/`.
